# Camera ecosystem integration research (2026-10-17)

This is technical planning, **not** a claim of working Ocularium app-account access or support for every camera.

## ANRAN keyring account recall (offline)

The native ANRAN form now offers opt-in storage of a single account/password and registration country/dial code through Linux Secret Service (`secret-tool` from libsecret). The secret payload travels via the subprocess standard input, not a shell, process arguments, copied reports, Ocularium registry or public Git history. The saved entry uses only static selectors `application=ocularium` and `entry=anran-v1`. On selecting the verified ANRAN app, a worker restores fields asynchronously without starting a vendor request. A user must still independently confirm app pairing, explicitly consent to possible phone logout, and click Connect for each one-shot lookup. The panel supports local deletion and fixed errors if the keyring is unavailable. Offline fixtures validate serialization/bounds and consent isolation; no real account was contacted. Before first save the user enters credentials once because old versions intentionally never stored them.

## Current implemented local video intake

Ocularium can now take **one** frame from an explicitly supplied local HTTP MPEG-TS source using a CPU ffmpeg decoder. This is a generic handoff for a future authorized local bridge, not a bridge implementation or cloud API client.

Security properties:
- Accepts only numeric loopback or private IPv4 HTTP URLs with explicit port and path, no URL credentials, query, or fragment.
- Uses an internal HTTP reader with proxies and redirects disabled, no DNS and no cookies.
- Streams bounded bytes to ffmpeg via stdin; the decoder never receives endpoint URL or cloud credentials.
- Times out decoding, caps video bytes, keeps the result as a transient egui texture.
- Endpoint is held only in application memory, never persisted to registry or included in copied reports.
- The optional source requires an external compatible endpoint; ordinary Ocularium discovery remains a standalone native app.

## Native Rust Meari VVP protocol groundwork (offline)

`src/meari_vvp.rs` implements bounded plaintext VVP media-frame parsing, sequence/keyframe replay gating, the 60-byte authenticated VVP command **encoder**, and explicit P2P transport selection from the authoritative logged-in device record's `deviceP2P` field. All code is pure and in-process: it sends **no** packets, contacts **no** cloud or camera, imports **no** Python runtime, and stores **no** credentials. Tests use synthetic device records and frames with fictitious authentication keys.

Protocol layout reviewed against the MIT-licensed community source:
- `custom_components/cloudplus/p2p_streamer/protocol.py`: command byte order, magic, MD5 material and command IDs
- `custom_components/cloudplus/p2p_streamer/codec.py`: per-frame payload offsets, timestamp and sequence
- `custom_components/cloudplus/p2p_streamer/engine.py`: transport selection from `deviceP2P`

**Explicit UDP socket I/O (not a working camera session):** `src/meari_ppcs_udp.rs` implements a native synchronous IPv4 UDP socket adapter with explicit interface binding (no wildcard bind), bounded datagrams, 75 ms receive polling, 250 ms write timeout, sender address capture, transient zeroizing buffers, and automatic socket closure. It implements `DatagramIo` and can drive the already-bounded PPCS one-shot controller; the controller's advertised local address must match the actual bound socket or nothing is transmitted. A candidate result is labeled *unverified* and never passed into playback. Real loopback-only tests exercise socket send/receive plus the legacy packet codec, timeout, truncation rejection, and bind mismatch. **No production caller invokes this adapter**: there is no GUI opt-in, camera targeting, DNS resolution, automatic initialization, or authenticated peer/session establishment. The code does not contact any household camera.

**Bounded offline PPCS probe orchestration:** `src/meari_ppcs_probe.rs` combines the separate PPCS parsing/cipher/discovery primitives behind an explicitly invoked one-shot controller, provisioned only by a session-only camera record with the authoritative `deviceP2P=ppcs` transport and its `deviceUUID` / `p2pInit` values. It requires a caller-supplied list of relay IPv4 endpoints and local socket address; an eventual network caller must resolve those endpoints from the init's root hosts and verify the mapping before proceeding. Construction sends no packets. Through an injected datagram I/O interface, the controller can send a single 0x00 hello and 0x20 rendezvous request per relay, process a validated root 0x40 peer offer, transmit a bounded 0x41 candidate challenge and recognize a matching 0x42 candidate response. Max eight root endpoints, four offers, 48 sends, 64 receives, and a five-second deadline; no background retries. Synthetic tests cover spoofed/mismatched packets, budget expiration and aborted sends. **The output is only an unverified candidate, never authenticated device access.** There are no concrete UDP sockets, DNS lookup, account requests, stream playback, or automatic calls from the GUI. A later live adapter must independently establish session trust despite the PPCS cipher's lack of integrity.

**Unique saved-camera PPCS comparison (counts only):** A separate `MatchedPpcsSummary` computes a strict one-to-one MAC correlation between the selected-LAN saved ANRAN cameras and the already-authorized transient account catalog, after owner/shared-home merging. Only exact unique normalized MACs on **both sides** qualify. For those matches, the report distinguishes cameras declaring PPCS (with syntactically valid or incomplete identity/init/host-key prerequisites), modern signaling, and unknown transport. Ambiguous, missing, or invalid MACs, model names, IPs and app branding do not establish identity; unmatched cloud PPCS cameras cannot inflate matched readiness. The summary is fixed-count only, with no IDs, MACs, keys, relay hosts, account data or access tokens crossing to the UI. No HTTP, DNS, UDP, credentials persistence, or background probing is added. A unique MAC match plus complete-looking protocol fields still does not cryptographically authenticate a device or authorize streaming.

**Live-account PPCS metadata preflight (counts only):** The existing one-shot ANRAN account worker now computes a redacted `PpcsMetadataSummary` directly from ephemeral, authenticated owner/shared-home catalog records before discarding them. Only records with `deviceP2P=ppcs` are examined; model `b81`, an ANRAN app label, an IP address, or even a populated host key without that declaration never implies PPCS. The report distinguishes missing versus syntactically invalid factory UUID, initialization string and host key. Parsing the init checks relay-host shape and uses temporary derived packet cipher state only; it neither resolves nor contacts roots. The result has counts only and is sent to the GUI alongside existing coverage and MAC-correlation counts; it never includes a DID, host key, init text, relay URL or MAC. **'Fields syntactically valid' does not verify the device's actual protocol, identity, account privileges, network reachability, or permission to stream.** An incomplete owner/shared list yields a partial view. Zero additional HTTP requests, socket calls, retries, persisted secrets, or automatic playback.

**Offline PPCS discovery preflight:** `src/meari_ppcs_discovery.rs` now decodes the pinned reference's factory-9 `deviceUUID` transformation into a 20-byte DID and its `p2pInit` rolling-byte root-list format. It retains normalized relay hosts and only the derived packet-cipher state, not a raw stored packet key; the supplied initialization data must come from a future authorized camera record. A strict bounded decoder accepts the PPCS 16-byte IPv4 sockaddr format (little-endian port, reversed IPv4 bytes) and rejects malformed/null destinations. A pure rendezvous preflight checks that 0x40 offers come from explicitly allowed root IPs and root-port range, then accepts only candidate 0x41/0x42 responses with the exact DID from an offered IP and a three-port hole-punch radius. It caps candidate counts and has an offline synthetic packet-codec→offer→candidate-response integration test. **A matching DID and source IP do not cryptographically authenticate a peer.** No DNS resolution, socket, outbound packet, session establishment, user credentials, or household camera interaction is implemented here.

**Offline PPCS packet envelope/cipher (not peer authentication):** `src/meari_ppcs_wire.rs` implements the legacy `0xF1 | packet_type | u16_be(payload_length) | payload` wire format and the four-byte-state chained substitution cipher from the pinned `ppcs.py` reference. A short-lived codec accepts a caller-supplied authenticated-session key and stores only its derived cipher state; encrypted packet buffers and decoded payloads are zeroized on drop. It enforces exact length matching and a 16 KiB input cap, with fixed wire-vector tests and an offline channel-receiver integration test. **The cipher is reversible obfuscation with no MAC or authentication tag.** An apparently valid packet is *not evidence of a genuine camera or peer*: actual authorized session establishment, remote endpoint binding, anti-spoofing and packet-origin validation are future work. The module performs no network calls, key guessing, endpoint discovery, or camera access.

**Offline legacy PPCS reliable channel/media intake (no network or encryption):** `src/meari_ppcs.rs` implements receive-side reordering for the eight reliable PPCS channels, with 16-bit sequence wraparound, duplicate suppression, a maximum 512-sequence lookahead, and at most 256 pending 1 KiB chunks per channel. It validates the authenticated/decrypted inner 0xD0/0xD1 data format and exposes ACK metadata for an eventual caller, but it does **not** send any acknowledgments or packets. It also reassembles the distinct PPCS 32-byte media header into bounded keyframe, predicted-frame and audio payloads with per-frame size limits. It rejects invalid types and overlarge buffers and resets on corruption rather than attempting speculative byte scanning. Inputs must come from a future authenticated, decrypted peer and from an explicitly selected media channel; none of this establishes a real PPCS session. The format and offsets are referenced to `p2p_streamer/ppcs.py` in the pinned community snapshot. This is separate from the VVP 0xFC/0xFD media header and must not be conflated with that parser.

**Offline PPCS media-to-decoder handoff:** `src/meari_ppcs_video.rs` ties an explicitly selected, separately verified media channel to the ordered legacy reliable-packet receiver and PPCS 32-byte frame parser. It accepts only *already peer/session-verified, decrypted* PPCS inner data packets, reassembles complete media frames, ignores audio, applies Annex-B H.264/HEVC SPS/PPS/VPS/IDR validation, suppresses replay/backwards sequence numbers, gates gaps until a recovery keyframe, and prepends cached parameter NALs when required. It returns transient zeroizing elementary-video samples compatible with `meari_video::decode_first_frame`. It provides ACK metadata without network transmission. Bounded batch size, output frame count, payload size and reset-on-corruption limit malformed input. Synthetic regression tests exercise packet reorder, media fragmentation, codec handling, recovery and optional FFmpeg CPU decode. **There is no authorization path from the unverified PPCS UDP probe into this module; playback awaits real authenticated media session verification.**

**Legacy VVP encrypted-frame decoding, independent of PPCS packet cipher:** `src/meari_stream_crypto.rs` implements the pinned `codec.py` fixed-key 3DES-EDE3 ECB transform for complete, already-reassembled VVP video frames. The vendor-key literal is not a camera password; it is padded with zero bytes to 24 bytes. It decrypts at most 0x80 bytes beginning at offset 0x30 for I-frames or 0x28 for P-frames, aligned to whole eight-byte blocks, then strictly verifies a single complete video frame with a plausible Annex-B payload before forwarding it through the existing VVP H.264/HEVC keyframe gate. The caller must explicitly choose plaintext or legacy encryption per trusted stream session. Independent Python-cryptography known-answer vectors, malformed and incomplete frames, wrong-mode rejection and codec-state recovery are tested offline. **This is not video-password/E2EE decryption, does not authorize a camera, does not authenticate a peer and is never connected to startup or the GUI.**

**Offline codec handoff (no camera account or transport):** `src/meari_video.rs` consumes only *complete, reassembled, already decrypted* VVP video frames and extracts bounded H.264/HEVC Annex-B access units. It requires SPS/PPS for H.264 or VPS/SPS/PPS for HEVC and matching keyframe NALs, preserves sequence continuity, and waits for another keyframe after gaps. Cached parameter sets can be prepended to a recovery frame. It refuses unrecognized/encrypted-looking bytes rather than trying to decrypt or guess. The standalone CPU decoder accepts these elementary bytes on ffmpeg stdin, without URLs, a server, or GPU access; its output is a single bounded in-memory RGB frame. The synthetic tests do not establish actual camera compatibility. **Neither account authentication nor P2P delivery is connected to this offline module yet.**

The user-observed ANRAN camera's **platform b81 is not its P2P transport field** and therefore cannot establish Meari compatibility or whether it uses modern signaling versus legacy PPCS. A matching app name alone does not validate the account backend. Live video still requires account-authorized device discovery, verified transport/signaling and key management, authenticated PPCS packet decryption where applicable, codec/media decryption where enabled, and delivery of complete codec frames to the native decoder.

The module intentionally rejects zero-length or excessively large media payloads and never attempts to decrypt data guessed to be plaintext. Payloads only become usable after the future authorized transport layer has reassembled them.

## Malformed HTTPS response classification without network retries

The bounded HTTPS transport can return `InvalidReply` before the JSON parser sees the response (notably if it exceeds its 512 KiB byte limit). The previous stage classifier mapped this to **network, TLS or timeout failure**, which could incorrectly imply that no response was received. Default/home diagnostics now preserve the fixed **unexpected response** category for rejected replies, and shared-home error counters count these as malformed rather than HTTP/network failure. The same rule applies to impossible local request/server states; genuine transport failures and coarse HTTP statuses remain distinct. An offline five-request mock exercises the successful redirect and login plus per-stage errors; no extra real requests, retries, credentials, URLs, response bodies, or saved identifiers are introduced.

## Numeric ANRAN catalog status and category parity

The pinned reference converts default and shared-home device-list result codes to strings; Ocularium previously rejected a numeric JSON `1001` as unauthenticated, and a numeric `1107` as an invalid shared-home reply. The catalog now recognizes numeric and string values for success (1001) and temporary failure (1023), and the shared-home empty code (1107), while retaining the existing strict treatment of redirect/login/home-list replies. It also recognizes reference NVR, neutral-NVR, base, and chime collections without manufacturing cameras from accessories; checks malformed known collections; handles directly nested camera objects in a `result` array; and infers battery class from string `devTypeID="5"`. Offline fixtures test all of these cases. No extra account requests, retries, credentials, P2P, or persistent data are introduced. This correction does not prove whether the prior US account response contained a numeric code.

## Device catalog shape validation

The native `meari_devices` parser now treats an HTTP-successful response with `resultCode=1001` as a verified empty catalog **only** when the `result` is an explicitly empty object/array or has recognized `ipc`, `snap`, `doorbell`, or `deviceList` array structure (possibly inside known nested home collections). It now checks **every recognized camera-list field**: a malformed sibling list cannot be concealed by an empty `ipc` or `deviceList` array. Missing `result`, null/scalar contents, unrecognized nonempty collections, and known collection keys with incompatible value types are classified as unexpected shape rather than no cameras. The normal device-list failure summary maps these to a fixed unexpected-response label; it neither persists nor prints vendor reply details. This avoids confusing a backend/protocol mismatch with a genuinely empty account and does not generate further network traffic.

## Redirect-provided country-code parity

The reference client updates `country_code` from a successful API redirect response before its login and signed catalog requests. Ocularium now follows that behavior only when the returned `result.countryCode` is a two-character uppercase ASCII country code. It does not change `phoneCode`, does not use country code to choose an unapproved API origin, and rejects invalid country values before sending any login. The existing HTTPS origin allowlist still applies. Synthetic tests prove the redirect country's effect on subsequent wire request fields and the absence of new requests/retries; no account data is recorded.

## Local GMT offset in signed ANRAN timestamps (offline parity)

The pinned reference `_base_params` creates `timestamp` from local civil time and includes its GMT offset, but Ocularium previously forced `GMT+00:00` on every machine. The native clock now captures the local offset for each timestamp and generates the corresponding signed value, with the same `t` / `signatureNonce` millisecond epoch. The independent UTC HMAC test vectors remain stable because fixture stamps explicitly use zero offset. Additional synthetic cases verify -06:00 and +05:30 offset formats and reject impossible offsets. No account login, retry, or new network request was added. This removes a wire-format mismatch but does not prove the old camera-list failure's cause.

## ANRAN nonce-format parity (no additional account traffic)

The pinned reference generates an eight-digit decimal redirect query `nonce` separately from the six-digit decimal `X-Ca-Nonce` header. Authenticated requests use fresh six-digit header nonces. Ocularium previously reused one 12-character hexadecimal nonce for both. The native request builder now uses independent numeric values derived from OS-backed randomness and rejects malformed inputs. Synthetic tests validate both wire fields without accessing an account, changing the request budget, or claiming this caused the previous camera-list failure.

## ANRAN single-shot request timeout parity

The upstream Python client configures `HTTP_TIMEOUT = (10.0, 30.0)` for connection and response reads. Ocularium's opt-in HTTPS transport previously used a 5-second connect and 8-second read budget. That is an observable mismatch which could reject a slower default device-list request even if a quick home-list request succeeds. The native transport now permits 10 seconds to connect and 30 seconds for the read, retaining its existing 8-second write limit, redacted status handling, one-shot request schedule, and no-retry guarantee. This trades a longer worst-case wait for compatibility; it is not evidence that timeout caused earlier failures.

## HTTP client parity and post-login status classification

The pinned `api.py` configures a fixed mobile `USER_AGENT` for its HTTP session, while Ocularium previously used the library default. `HttpsExchange` now supplies the pinned value for every consented request, including redirect and login. This is an observable request-header parity correction, **not a claim of confirmed camera compatibility**. Instead of reducing every HTTP failure to generic `Transport`, the exchange converts HTTP statuses into fixed categories: permission denied (401/403), route unavailable (404/405), throttling/timeout (408/429), upstream failure (5xx), and other HTTP errors. Network/TLS/timeout errors remain independent. Only these labels are propagated through `DeviceListDiagnostic`; no status-code string, response body, URL, remote message, account identifier or access token enters logs or UI. Offline tests exercise the pure classifier and a synthetic partial-success sequence with successful home/device lookup and a failed default list. No automatic retries, additional calls, login, UDP or camera streaming were added.

## Signed ANRAN request parity with pinned community reference

Static comparison against the pinned `custom_components/cloudplus/api.py` showed Ocularium incorrectly propagated `localTime` into `_base_params`-equivalent requests after login. The reference sends that field for account redirect and login, but not for token-signed default-device, home, shared-home or IoT-platform requests. HMAC-SHA1 signs all request fields, so the additional value changes the outgoing signature. Ocularium now inserts `localTime` **only** for redirect and login, and uses the same post-login field shape as the community reference. An independent Python HMAC/base64 vector checks deterministic `US`/`1` post-login signatures and prevents reintroducing the stray field. The reference also accepts a successful home-list response that simply omits `homes`, so Ocularium treats that case as an empty list while still rejecting invalid non-array `homes`. No real login, DNS, P2P or streaming occurs from this correction. It may explain the observed US-account failure, but hardware QA has not established that.

## Redacted post-login endpoint diagnostics

Human QA on a US-registered ANRAN account showed a successful-looking login followed by the generic "No verified device list" error. The native client previously swallowed both the default-device and home-list endpoint failures into that one result. The account client now classifies each into fixed labels: accepted, HTTP/network failure, temporary vendor unavailability, rejected or unexpected response; when shared-home lists were attempted it also counts their HTTP, rejection and malformed outcomes. Failed post-login catalog discovery now carries only these summary categories into the existing consent-gated GUI; raw responses, user IDs, tokens, home IDs, account info, URLs and error strings are never exposed. Synthetic tests cover US-region account fields, transport failures, vendor status differences, malformed response shapes, and accepted empty catalogs. **This does not change request order, endpoint selection, user permissions or retry policy.** No fresh credential attempt is required for this implementation.

## Authenticated Meari device-list normalization (native Rust, offline)

The new `src/meari_devices.rs` implements an **in-memory, bounded parser** for the camera-list response a future authenticated Meari-family account client may receive. It covers account-owned and shared-home device groups, deduplicates repeated `deviceID` records without cross-merging different devices, and classifies `ipc`, `snap`, and doorbell categories. A successful response marker is required; the `1023` transient code is recognized separately. **A marker in JSON does not authenticate a response by itself**: the future client is responsible for making the authenticated HTTPS request and verifying the server.

It retains session-only fields needed by a future media adapter, including `deviceP2P`, `hostKey`, `p2pInit`, `deviceUUID`, and `snNum`, but these types have no Debug/Serialize capability and are **not saved to the existing registry**. The only public diagnostic is a count of cameras/categories/transport declarations; secrets, addresses, MACs, and device IDs are never included. Strict JSON-size, recursion-depth, and record-count limits prevent unbounded input from an upstream API. A future account integration must define the credential/token lifecycle and avoid diagnostic exposure before this parser is wired to real logins.

Local inventory correlation is **MAC-only**, if the backend actually supplies a syntactically valid MAC. We explicitly refuse identity assertions from IP, hardware chipset, app name or firmware model. A cloud API device list that does not include a MAC is not automatically linked to a LAN device. The known household ANRAN camera still has **unverified Meari backend compatibility**.

**One-shot in-memory MAC comparison:** When an explicitly consented account attempt succeeds, Ocularium compares the returned catalog against only the saved, user-labeled ANRAN camera records for the *currently selected LAN scope*. No registry data is transmitted in account requests. The result provides **aggregate counts only**: exact one-to-one MAC matches, ambiguous duplicate MAC groups, saved records lacking usable MACs, saved records with no matching cloud MAC, and cloud cameras without usable MACs. Duplicate MACs on either side are deliberately ambiguous. Missing matches are inconclusive: MACs may be omitted by the backend, the camera may be saved under a different app, or the current scope may not contain it. This is not a device-stream capability claim. All comparison identifiers and catalog material are temporary; no account keys, IDs, or match outcomes are added to the registry or reports.

This is another protocol milestone, **not** working camera account discovery, live stream authentication, or proof of video access.

## ANRAN account handshake (experimental, one-shot opt-in)

The new native `src/meari_account.rs` implements an **explicit, three-stage** ANRAN wire exchange using the community profile's reported `sourceApp=84`, `partnerId=84`, app version and phone-type metadata. It constructs (1) redirect, (2) **one** login attempt, (3) an authenticated default device list, (4) an authenticated home-list query, and (5) at most **eight** signed per-home list requests, deduplicated and bounded. The read-only shared-home calls are modeled on the community reference's `GET /v1/app/home/list` and `GET /v1/app/home/join/device/list` with `homeID` and `funSwitch=1`. A recognized `1107` empty shared-home reply is not counted as a failure; malformed or rejected responses cause explicitly partial coverage without retries. Default and shared devices deduplicate only by authoritative `deviceID`. The legacy DES-CBC and AES-CBC compatibility formats, HMAC-SHA1 `X-Ca` request headers, and signed device-list form are checked against independently computed fixed-answer vectors. Failed login stops immediately; it never mutates the password or retries automatically.

The module's protocol logic is mockable and tested without touching any real camera or account. A native certificate-verifying HTTPS transport is exposed only via an **explicit one-shot consent gate**. Ordinary startup, LAN discovery and camera selection do not contact the cloud service. It enforces an allowlist of known Meari/CloudEdge host families, prohibits unvalidated redirect targets, disables proxies and HTTP redirects, bounds response size, and returns error categories rather than server bodies or credentials. Account/password and token values are short-lived `Zeroizing<String>` values in memory; the existing camera registry does not store them.

**Backend preflight (offline):** The panel starts with **Unknown / not checked** and keeps all account inputs hidden until the user explicitly selects **ANRAN app** *and* affirms that this particular camera appears in that app's device list. Other app choices remain blocked; switching choices clears existing credentials and consent. The checked app is transient and is **not** persisted as a verified hardware property. Only a subsequently authorized, authenticated device-list response can test whether the account backend actually contains the camera; it still cannot prove playable P2P video.

**GUI safety boundary:** Account and password fields are masked, held temporarily using zeroizing memory, and cleared from the GUI on submission. No login occurs unless the user explicitly authorizes that one attempt and acknowledges the potential mobile-session conflict. Only a redacted device-count, local-MAC-correlation and coverage summary or generic error reaches the UI; tokens, device IDs and camera keys are never exported or persisted. The temporary catalog is discarded after summarization. The client zeroizes its owned request-value, plaintext credential, response-byte and catalog-field buffers on release as a best-effort measure; the HTTP library and operating system can still create transient copies. No retries or background polling are implemented.

**Optional IoT platform config inspection (default OFF):** The ANRAN GUI exposes a separate checkbox for one signed, same-origin `GET /v2/app/config/pf/init?iotType=4` during an already-consented account lookup. It is never called by startup, LAN discovery, or ordinary account login unless this extra option is checked. The response may contain OpenAPI credentials, MQTT broker configuration, and encrypted platform signatures. Ocularium reads only non-secret **presence flags** (OpenAPI, MQTT, platform, encrypted-signature declared) into an aggregate summary; it neither decrypts the signature nor connects to any returned service address. Malformed data, an HTTP failure, or the vendor's transient `1023` response produce fixed statuses and **no retries**; default and shared-home discovery proceed independently. Platform bytes are transient, not saved or included in reports. Presence does not prove working P2P transport or connectivity.

**Current limitations:** The ANRAN community protocol may not match this particular device, some app logins may displace a concurrent mobile session, and a verified live account/device exchange has not been performed. The handshake now covers default and bounded shared-home camera lists and optional read-only IoT configuration inspection, but not platform credential decryption or P2P platform authorization. Responses can still be incomplete, for example after an unavailable home list or a cap of eight shared homes. A successful API response would still not prove video support or transport compatibility. This remains an experimental implementation, not an authorization to connect to any third-party account.
